1.1 · Ventive — AI R&D Tax Credit Platform FLAGSHIPDEMO

FinTech / TaxTech

Client: a US R&D tax-credit advisory firm, delivered through Ventive  ·  Role: lead AI engineer across six services, from architecture and PRDs to code, review and rollout  ·  Timeline: 2026, multi-release and ongoing  ·  Demo: Contract analysis walkthrough ↗

A platform that takes a tax firm's engagement from raw client documents to a signed, client-ready credit letter. AI agents read the contracts, extract the tax documents, compute the credit and fill the deliverables. Analysts approve at each gate, and the system learns from their corrections.

The problem

  • Payroll, ledgers and returns keyed into Excel workpapers manually.
  • Credit computed, forms filled and letters written per client, hours each.
What I built

  • Form-aware extraction for W-2, 1099, K-1, ledgers and census files.
  • A rules-driven credit engine that fills workpapers, forms and the letter.
The outcome
  • Documents in Drive flow to a filled workpaper with no one touching them.
  • Contract verdicts agree with the firm's own answers ~86% of the time.
  • Cost per analysis cut by a third; a 51-minute extraction now takes 7.

The problem

An R&D tax credit study is mostly reading and arithmetic done by expensive people.

  • Contracts: each one must be read to decide whether the customer "funded" the research, which removes it from the credit.
  • Documents: payroll, ledgers and prior returns arrive as scans, spreadsheets and PDFs and are keyed into Excel by hand.
  • Calculation and delivery: the credit is computed under several methods, filled into Form 6765 and state forms, and written up as a letter.
  • Consistency: each step took hours per client and the answer depended on which analyst did it.

The firm wanted the whole chain automated, with a human approving at the points where judgement or liability sits.

Architecture

One admin API owns the shared Postgres schema and every integration. The three AI engines are separate services that never write each other's tables. Requests go over HTTP; completions come back on one Redis event channel, so the gateway can fan out, wait, reconcile and re-drive without any engine knowing about the others.

The six services

  • Admin UI (React 19, TypeScript): engagement timeline with live progress, batch upload and bundle review, analysis reports, an agentic chat for correction re-runs, editors for rules, prompts and memories, workflow authoring, run audit, letter and form cards.
  • Admin API gateway (FastAPI): the only writer of the shared schema. Orchestrates batches, hosts the automation bus, fills workpapers and forms, renders letters, fronts Drive, Gmail, DocuSign and S3.
  • Contract analysis engine (FastAPI, LangGraph, Celery): the agent graph, per-node case-law and memory retrieval, pause and resume, streaming chat with tools, correction distiller, stall watchdog, per-node cost events.
  • Tax-form extraction (Python, Textract, LLM): classifier, per-form handlers, ledger and census lanes, reconciliation, Neo4j structuring.
  • Calculation engine (Python, FastAPI, Celery): pure compute with a thin IO shell, readiness checks and claims so a fill runs once per input, AI merge agents with source guards.
  • Text extraction (FastAPI): classifies each PDF as text, image or hybrid and routes to native text or vision OCR, with warnings that gate low-quality input.

How it works

A contract, start to finish

  1. Upload and bundle. Files are grouped into contracts by filename pattern, then by an LLM for the ambiguous ones. The analyst confirms the bundles and picks the taxpayer.
  2. Document check. The engine extracts eight verbatim clause families (IP, payment, termination, governing law, incorporated clauses and more), folding in clauses incorporated by reference.
  3. Triage. If the contract is silent on something that matters, the run pauses with questions. The analyst answers in chat and the run resumes.
  4. Two prongs in parallel. A rights test (who owns the research) and a payment-risk test (who bears the cost of failure), each grounded in retrieved case law.
  5. Challenge. An adversarial review argues the other side; an IRS counter-argument step writes what an examiner would say.
  6. Verdict. One derived-verdict step merges the prongs into qualifies / does not qualify, a confidence score and a tax position. It is the only node allowed to write the verdict.
  7. Review and learn. Low-confidence results wait for review. A correction re-runs only the affected nodes, and an accepted correction becomes a lesson for future runs.

A document, start to finish

  1. Arrival. A file landing in the client's Drive folder emits an event. Content-hash dedupe stops re-uploads from running twice.
  2. Plan. The gateway works out what the engagement still needs (which forms, prior years, states) from the rule bundle and submits only those.
  3. Extract. Each chunk is classified and routed to its form handler. Multi-page and multi-copy forms are merged. Ledgers go through layout inference and a balance walk.
  4. Reconcile. W-2 totals are checked against the W-3 per EIN and year with cents-level tolerance.
  5. Fill. When the inputs are complete, the calculation service claims the fill and the AI merge agent writes the workpaper rows, every value checked against its source.
  6. Calculate and deliver. After workpaper approval, the engine computes the scenarios, the analyst accepts or overrides, and forms and the letter are generated and sent.

Agent engineering

  • Schema-constrained outputs: every node returns strict JSON against a wire schema with a parse backstop. A malformed answer is retried once per failure kind, never silently accepted.
  • Selective re-runs: node outputs are captured at completion. A correction marks the nodes it touches dirty and re-runs only those and their consumers, derived from what each node reads.
  • Prompt caching: the contract is sent once as a cached block and reused by the six nodes that read it. Moving response schemas off the wire kept the cache key stable. Same contract: $3.31 → $2.16 per run.
  • Reasoning tiers: mechanical nodes run at low effort, analytical nodes at medium. Output tokens fell 22% and wall-clock 21% with an identical verdict.
  • Safety rails: abort probes with heartbeats between nodes, a 10-minute stall sweep that fails closed on Redis outage, publish-after-commit so no event precedes its data, and scrubbing of model text that could forge a prompt frame.
  • Correction memory: lessons are embedded before they are saved, retrieved per node by cosine similarity (pinned lessons always), and stamped on each run so the report shows which memories were considered and applied.

Human in the loop

The system pauses where judgement sits, and every gate leaves an audit row:

  • Triage questions before analysis, and bundle review before dispatch.
  • A pending-review state for low-confidence verdicts.
  • Workpaper approval before calculation; accept or override the recommended scenario with a required reason.
  • A five-minute chat card to approve, edit or reject each distilled lesson.
  • A reviewed-narrative gate before a letter can be finalized.

2.1 · Real-Estate CRM Intelligence Layer LIVE

PropTech / Real Estate

Client: a high-volume residential real-estate agent and their four-person team  ·  Role: sole engineer, design through production operation  ·  Timeline: Jul 2026 – present, live since Oct 2026  ·  Code: private repo, 246 commits

An AI layer between four systems that do not talk to each other: Gmail, Follow Up Boss (people), Monday.com (deals) and Slack. It reads every email as it arrives, works out who each person is and what role they play, extracts the terms of attached contracts, and keeps tags, deal stages and notes in sync. It owns no data of its own and never writes without a confidence floor or a human rule behind it.

The problem
  • 300–400 emails a day and 40–50 closings a year, triaged by hand.
  • The old CRM had no API, so nothing could be automated.
  • Contacts, deals and conversations lived in four tools with no link between them.
What I built
  • A Gmail push pipeline with Claude classification, identity and contract extraction.
  • A memory of every person's role per property, ranked by evidence source.
  • An SLA state machine that escalates missed VIP messages to Slack.
The outcome
  • Validated by month-by-month dry-run replays of 500–800 real emails before any live write.
  • In production: 1,039 emails in the first three days with zero errors.
  • Next agent is a config change, not a fork.

By the numbers

The problem

  • Volume: hundreds of emails a day, many with contracts, disclosures and closing statements attached.
  • Identity: the same person appears as buyer on one property and agent on another; names are misspelt; trusts and LLCs hide the people behind them.
  • Sync: tags in Follow Up Boss and stages on the Monday deal board drifted apart, and nobody knew which was right.
  • Response time: VIP and in-escrow messages were missed because nothing tracked them.

Architecture

How it works

One email, start to finish

  1. Arrive. Gmail pushes a history id. The edge claims it and enqueues; the worker reads new messages under a single-flight lock.
  2. Classify. Claude returns the category, the property address in structured parts, and whether the mail moves a deal. Outbound mail is only classified if it carries a contract.
  3. Resolve people. Exact email match, else the identity prompt over candidates. New people are created only with an email address, per the client's rule.
  4. Read documents. Contracts, addenda and closing statements are extracted (prices, dates, parties, counters, with the latest counter winning). Closing statements can be pulled from Drive.
  5. Match the property. The LLM matches against live deals; a confident match links, an ambiguous one is refused.
  6. Update memory. Each person gets a live role row per property (seller, buyer, counterparty, professional…) with a stage and evidence quotes. Sources are ranked human > contract > board > thread > classifier > tags, and a human row is never overridden.
  7. Sync. Tags, deal stage, a dated note line and contact price are written to Follow Up Boss, each write logged with its cause. Deals move forward only.
  8. Watch the clock. A pending SLA opens for VIP and in-escrow senders and escalates to Slack if unanswered.

Agent engineering

  • Models by job: Haiku for property matching and closing-statement picks, Sonnet 5.5 with medium adaptive thinking for classification, contracts, roles and identity, Opus for client synthesis. Chosen on a 40-email comparison.
  • Prompt caching: the system prompt and policy context are cached; about 11.2k of 13.4k input tokens per call are cacheable.
  • Replay before write: each month's real emails were replayed in dry-run against a scratch database, every verdict reviewed, and defects fixed as versioned prompt changes before the next month went live. Prompts advanced from v24 to v32 this way.
  • Facts beat tags: a contract or a human row always outranks what a classifier or an old tag says.
  • Deterministic edges: the LLM judges; code builds the canonical address string and enforces stage order, thresholds and the "no contact without email" rule.

2.2 · PropertyAI CRM — AI Property Management on Buildium LIVEDEMO

  • Rent follow-ups, renewals, escalation and dispatch run unattended on a schedule.
  • Live two-way Buildium sync for tenants, leases, balances and work orders.

How it works

A tenant text message

  1. Receive. The channel webhook finds the tenant by phone and loads their active conversation.
  2. Compose. The prompt carries the tenant's facts (unit, rent, balance, lease end), the last 10 turns and matching knowledge articles.
  3. Reply and classify. Claude answers in plain language and appends a metadata block with the intent and urgency; regex parses it, and a canned apology covers an empty answer.
  4. Act. The intent handler creates the maintenance request, task, dispatch, escalation or renewal task, and the transcript is saved.
  5. Follow through. The hourly escalation job promotes stale high-priority tasks; open emergency maintenance older than four hours raises an urgent task.

  • Humans keep the pen: screening runs in assist mode and lease abstraction is confirmed by a person before terms are written.
  • Deterministic where it should be: listing copy, maintenance triage and lease abstraction are templates and rules with a documented swap to a model provider.

Enter a property and its comparable sales; get the after-repair value, five exit strategies, a 0–100 score, a stress test and an AI underwriting read. Every number comes from a deterministic engine. The model only interprets what the engine computed.

The problem
  • Underwriting a deal means the same spreadsheet math, repeated per property.
  • Investors want a read on strategy fit and an offer plan, not only numbers.
  • An AI that invents a cap rate is worse than none.
What I built
  • Pure-function engines for comps, ARV, five strategies, scoring and sensitivity.
  • An Underwriting Agent that streams fit scores and rationale over SSE.
  • A Negotiation Strategist that returns an offer ladder and scripts.

  • Agent orchestrator (FastAPI): watches for new tasks and runs each through five agents, pushing progress to the Studio over WebSocket.

How it works

A chat turn

  1. Route. A main orchestrator node decides the turn. Email and calendar requests go to their own decision → intent resolver → action chains; everything else passes an LLM domain classifier.
  2. Ground. Knowledge questions retrieve from the RAG service; personal questions hit temporal or cross-session memory recall.
  3. Answer. A tool-calling speaker node writes the reply, bound to knowledge search, web search, time and task creation. Only answer-writing calls stream to the user; routers stay internal.
  4. Pause when needed. Onboarding, daily-reminder and content flows stop with interrupt(), checkpoint in Redis, and resume days later with Command(resume=…).

A voice call

  1. Join. A warm worker joins the LiveKit room with no cold start. Silero VAD, a multilingual turn detector and noise cancellation handle the audio.
  2. Listen. Deepgram transcribes; a six-node graph (decide, greeting, general, memory recall, retrieval, content) handles the turn.
  3. Fast route. A clear product question skips the LLM router and goes straight to retrieval.
  4. No dead air. A short filler line is spoken the moment retrieval starts; the answer then streams sentence by sentence through Cartesia.
  5. Call to project. On hang-up the transcript becomes a titled session with 1–20 tasks, lanes and dependencies.

From tasks to finished work

  1. Pick up. The orchestrator takes new tasks as they are written and also polls the task table every 3 seconds, because voice-created tasks never call its API.
  2. Run. Up to three tasks at a time go through Omni (research), Planner, Builder, Reviewer and Nexus (write-up).
  3. Show. Each stage streams lane transitions to the Studio and stores output, timing and tokens; the last stage produces a downloadable report. Refine re-runs with a user instruction instead of starting over.

Agent engineering

  • Streaming end to end: on Python 3.10 nested LLM calls only reach the graph's event stream when a node hands down its run config, so each answer node passes it explicitly; the RAG service's own stream is relayed through the graph as custom events.
  • Graph controls speech: I patched the LiveKit LangChain adapter so the graph, not the plugin, decides what is spoken.
  • Resilience: every model call goes through OpenRouter with ordered fallback models and retries, so a rate-limited provider becomes a slower answer, not an error.
  • Knowledge: documents chunked to about 1,800 characters, embedded with text-embedding-3-small into Postgres with an HNSW cosine index. Each query retrieves at least 8 passages above a similarity floor plus the passage after each of the top four. Answers by Gemini 2.5 Flash Lite with GPT-4.1 mini and GPT-4o mini as fallbacks.

Multi-tenancy and platform

  • Tenant isolation: every request carries an organization, role and scopes; Redis state is keyed {namespace}:{org}:{user}:{session}; a middleware guard blocks cross-organization access.
  • Roles and scopes: six roles (platform admin through client viewer) map to {module}:{action} scopes, enforced per endpoint. I authored the architecture plans the team adopted for serving many clients from one codebase.
  • Delivery: shipped to GCP through GitHub Actions, later as 8 services on Railway (six apps plus Postgres with pgvector and Redis) with auto-deploy on merge and Playwright browser audits before release.

10.1 · OptiML — LLM Compression & Fine-Tuning Framework

AI Infrastructure

Organisation: OptiML (Log Two LLC), Apache-2.0-licensed framework  ·  Role: lead developer on the core framework; top contributor by commits  ·  Timeline: Apr 2024 – Jan 2026

A framework that makes compression part of fine-tuning: pruning, quantization, LoRA and multi-head latent attention as composable pieces of one training loop, driven by one config. I redesigned the core from a monolithic tuner into an event-driven system of callbacks, typed events and pluggable metrics, so a new technique is a callback rather than a change to the loop.

The problem
  • Each compression technique came with its own training script and duplicated statistics code.
  • Adding a method meant editing the training loop itself.
  • Configuration was scattered across code and scripts.
What I built
  • Config as data: a layered YAML template, Pydantic validation and a fluent builder.
  • An event-driven Tuner with a dispatcher, 23–25 callbacks and 35 typed events.
  • Projection interfaces for pruning patterns and pluggable importance and Hessian metrics.
The outcome
  • Magnitude, Wanda and SparseGPT pruning in three sparsity patterns on one API.
  • LoRA, QLoRA, QAT, AWQ, MLA and regrowth built on feature branches.
  • Multi-GPU training via DDP and lm-eval benchmarking built in.

Architecture

How it works

  1. Configure. A YAML layered on a full default template, validated into one typed object; callbacks are built from the config.
  2. Load and shard. Models load across GPUs with DDP; linear layers are wrapped as prunable layers with mask projections.
  3. Collect. A data-collection callback gathers activations in continuous, sampling or calibration mode; metrics (Wanda's running average, SparseGPT's Hessian) accumulate.
  4. Compress. Calibration pruning runs one-shot: collect → mask → log sparsity → optional eval; regrowth and compression callbacks act during fine-tuning on logical and micro steps.
  5. Adapt and merge. LoRA as W + α/r·BA with a low-rank metric and weight merging; adapters saved and loaded by the manager.
  6. Evaluate. lm-eval runs through the framework's model wrapper; results feed the team's benchmarks.

Pruning patterns as ad-hoc functionsProjection interfaces with a registry and aliases, so a new pattern is a class named in config.
Statistics duplicated per algorithmMetrics separated from algorithms behind one interface, chosen by a discriminated union.
Compression tangled with data collectionSplit into separate callbacks, which made regrowth during training possible.
Config scattered across scriptsOne base template with overrides and Pydantic validation; the Tuner takes a single object.

How it works

An employee onboarding
